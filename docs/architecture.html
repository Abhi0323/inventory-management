Factory Inventory Management System

Architecture overview: a Vue 3 single-page app talking to a stateless Python FastAPI service that serves in-memory mock data loaded from JSON files. There is no database.

System architecture

The system has three tiers: the browser, the API process, and static JSON files read once at startup.

Tech stack

The stack is small on purpose. There are three runtime dependencies on each side.

Frontend

client/

  • Vue 3.4 with the Composition API
  • vue-router 4 in HTML5 history mode
  • axios 1.6 for HTTP
  • Vite 8 dev server and build, port 3000
  • Node 20.19+ or 22.12+
  • Custom SVG charts and CSS Grid, no chart library
Backend

server/

  • Python 3.11+, managed with uv
  • FastAPI 0.110+ on uvicorn
  • Pydantic 2 response models
  • Port 8001, CORS open to all origins
  • Swagger UI at /docs by default
Data and testing

server/data, tests/

  • 7 JSON files, loaded once at startup
  • No database, ORM, or persistence layer
  • pytest + FastAPI TestClient (httpx)
  • pytest-cov for coverage
  • Backend tests only, no frontend test suite

Data flow

This example traces a filter change on the Dashboard to the re-rendered numbers.

Request lifecycle

  1. Filter state. useFilters.js keeps four module-level refs: period, location, category, and status. Every view shares them as singletons.
  2. Request build. getCurrentFilters() maps location to warehouse and period to month. api.js then turns that into a query string.
  3. Server filter. apply_filters() matches warehouse exactly and category and status case-insensitively. A value of all skips the filter.
  4. Time filter. filter_by_month() matches a substring on order_date. Quarters expand to three months through QUARTER_MAP.
  5. Response. Pydantic validates the result (where a response_model is set) and FastAPI serializes it to JSON.
  6. Render. The view stores the raw arrays in refs. Totals, charts, and tables are computed properties derived from those refs.

Shared composables

  • useFilters: the four global filter refs, hasActiveFilters, and resetFilters
  • useI18n: English and Japanese strings, saved to localStorage. The locale also sets the currency (USD or JPY).
  • useAuth: a hardcoded mock user with locale-aware fields. There is no real auth.

  • FilterBar: the global filter controls
  • Detail modals: Product, Inventory, Backlog, Cost, and ProfileDetails

  • utils/currency.js: currency formatting

Gaps and caveats

These came up while tracing the code. They're worth knowing before you change anything.

The client calls endpoints the server doesn't define. api.js has getTasks, createTask, deleteTask, and toggleTask (/api/tasks), plus createPurchaseOrder and getPurchaseOrderByBacklogItem (/api/purchase-orders). main.py has no such routes, so those calls return 404. App.vue calls the task methods.
Orphaned view. Backlog.vue exists but has no route in main.js.
Unused models. PurchaseOrder and CreatePurchaseOrderRequest are defined in main.py, but no endpoint uses them.
Hardcoded calendar. QUARTER_MAP and the quarterly report only know about 2025. Data from any other year falls through.
Global backlog count. total_backlog_items on the dashboard ignores every filter.
No persistence. Any write added later will only live in process memory and will be lost when the server restarts.
